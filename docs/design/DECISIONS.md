# VerySmartTV — decisions (ADR log)

One entry per decision in [DESIGN.md](DESIGN.md). Format: context → decision → alternatives rejected →
consequences. Every entry is **accepted** by the owner (2026-11-09) and is what [v0.1.0](https://github.com/itsluminous/verysmarttv/releases/tag/v0.1.0)
ships, unless its heading says **rejected** (the decision was not taken; the entry records why),
**changed** or **amended** (the decision as it now stands, with the date and the reason in the entry; the
amending ADR is named when it is another entry). No entry is superseded outright. ADR-038 to ADR-048 record
where the build departed from DESIGN.md; §20.2 there is the summary. The project was named VerySmartTV on
2026-11-09; the launcher's applicationId and namespace are `com.itsluminous.verysmarttv`, the Gradle module
stays `:launcher`.

## ADR-001 One Gradle project with five modules
- Context: three apps that share provider contracts, glass drawables and D-pad helpers, and must be signed with one key.
- Decision: `:core` (Java library), `:launcher`, `:traktshelf`, `:livescore`, `:testkit`; `build-logic` convention plugins; one version catalog.
- Rejected: three Gradle projects as in cleanyourtv (`launcher/`, `addons/traktshelf/` each with its own wrapper): duplicated signing/version code, no shared module without publishing, three CI matrices.
- Consequences: one `./gradlew ci`; the emulator job installs all three debug APKs from one build; a change to a contract fails the other side's compile.

## ADR-002 AGP 9.x / Gradle 9.x / JDK 17
- Context: cleanyourtv pins AGP 8.5.2 + Gradle 8.9 (JDK 17–22 only); HikViewer (the owner's other repo) pins AGP 9.5.1 + Gradle 9.8.2; the local SDK has build-tools/platform 37.
- Decision: take the current stable AGP 9.x and Gradle 9.x at Phase 0; JDK 17 everywhere.
- Rejected: staying on AGP 8.5.2 to match the carried build files (two toolchains for the owner; JDK ceiling at 22).
- Consequences: AGP 9's built-in Kotlin compiles `:livescore` without KGP; build files are rewritten in Kotlin DSL during the carry.

## ADR-003 compileSdk 36, targetSdk 34, minSdk 26
- Context: carried `launcher/app/build.gradle` has `minSdk 26`, `targetSdk 34`; presets cover Android 8.0 TVs; no Play Store requirement.
- Decision: compileSdk 36 (installed), targetSdk 34 shared by the three apps, minSdk 26.
- Rejected: targetSdk 35/36 now (edge-to-edge and service/intent tightening untested on a TV with accessibility + notification-listener services); minSdk 29 (would exclude TVs the presets serve).
- Consequences: a Phase 6 follow-up re-evaluates targetSdk on a real Android 14 TV.

## ADR-004 Java for carried code and `:core`, Kotlin for `:livescore`
- Context: 101 carried Java files with no tests of their own; the launcher ships no Kotlin stdlib (`packagingOptions` excludes `kotlin/**`); new code is a networking/parsing app; the owner writes Kotlin daily.
- Decision: keep Java in `:launcher`, `:traktshelf`, `:core`; write `:livescore` in Kotlin (stdlib only).
- Rejected: all-Java (new code in the language with weaker null-safety and more boilerplate); all-Kotlin (a multi-week conversion with no visible result, stdlib in the launcher, regressions in untested code).
- Consequences: two languages in one repo, isolated per module; `:core` must stay Java so the launcher pulls no stdlib.

## ADR-005 No coroutines, no serialization/HTTP libraries in `:livescore`
- Context: four URLs, payloads up to 365 KB, a 1 GB TV, traktshelf already uses `HttpURLConnection` + `org.json` + threads.
- Decision: `HttpURLConnection`, `android.util.JsonReader` streaming parse, a single-thread `Executor`, `Handler`.
- Rejected: coroutines (+~200 KB after R8, a second concurrency idiom), OkHttp/Retrofit/Moshi/kotlinx-serialization (dependency weight for four endpoints), `org.json` tree parsing (holds ~3 MB of objects for the tennis payload).
- Consequences: parsers are hand-written against fixtures; adding a field means editing a parser and a fixture.

## ADR-006 Views + RecyclerView, no Leanback browse fragments, no Compose
- Context: carried UI is Views; traktshelf avoided Leanback; Compose for TV is ~2 MB.
- Decision: Views everywhere, shared glass drawables in `:core`.
- Rejected: Compose for TV (size, 1 GB TVs), Leanback `BrowseSupportFragment` (heavy, opinionated).

## ADR-007 Decompose `MainActivity` into 17 classes with pure rule objects
- Context: 4,973 lines, 180 methods; focus and layout decisions are inline `if`s, untestable without a device.
- Decision: §8 table; "move verbatim first, refactor second"; every focus/row decision becomes a pure class returning a value; a Gradle check fails files over 1,200 lines.
- Rejected: leaving it (no unit tests possible for the Up→score→Inputs rule); a rewrite (loses years of device-specific fixes encoded in that file).
- Consequences: Phase 2 is the riskiest phase; the Espresso focus suite is written before the split and gates every commit of it.

## ADR-008 Drop decorative and superseded launcher features (accepted)

## ADR-014 Refresh-on-read plus JobScheduler, no services
- Context: 1 GB TV; a 60 s interval is below JobScheduler's 15-minute periodic floor; nothing should run while nothing displays.
- Decision: §13.5: the launcher's 60 s provider read (only while a followed event is live and Home is resumed) triggers a stale-check fetch; the scoreboard UI polls at 30 s while resumed; a one-off job 2 min before the next followed start and a 6 h periodic fixture refresh; backoff 1-2-4-8 min.
- Rejected: a foreground service with a notification (the TV shows it, and it costs memory all day); `AlarmManager` at 60 s (wakes the device with nothing on screen); polling from the launcher itself (it has no INTERNET and must not).
- Consequences: the pill's freshness depends on a screen looking at it, which is the point.

## ADR-035 All user-facing text lives in string resources
- Context: owner's rule, added with the ADR-008 answer; the carried code has a few literals (`"LIVE"`-style kickers, settings subtitles) and the decomposition will touch every one of them.
- Decision: no literal that a user can read is written in Java or Kotlin, in any module. Everything goes through `R.string` (with `%1$s` placeholders where the text is composed). Lint's `HardcodedText` and `SetTextI18n` are errors; a module may not baseline them.
- Exempt: text that is data rather than UI (a companion's `line`/`meta` row the launcher renders verbatim, log messages, exception messages, JSON keys).
- Rejected: enforcing it only in the launcher (the companions have the same 30-locale fallback problem) or by review alone (lint catches it for free).

## ADR-036 Compatibility with the fork's files is by shape, not by name
- Context: §7.4 says the order reader also accepts the fork's `tvhome-order 1` header and a backup whose `package` is one of the three known names, and §14.2 asks for `OrderMagicTest` and `BackupCompatTest`. ADR-010/011 say the old identifiers may appear nowhere in code or tests: the identifier gate in docs/BUILDING.md prints nothing. The two cannot both hold for a literal.
- Decision (Phase 1 coder, 2026-11-09): `Order.decode` accepts any header matching `[a-z]+-order 1` (the format is unchanged; only the product name in the header moved), and `Backup.restore` checks `version` and `prefs` and never reads `package`, as it already did. The tests use stand-in names (`previous-order 1`, `com.example.previouslauncher`) that exercise the same code path. The fork's files restore without the old names being written anywhere in this tree.
- Rejected: spelling the old literal in code or a test fixture (fails the gate, which is the project's one defence against a half-done rename); building the literal from pieces (`"tv" + "home"`) to slip past the gate (hides exactly what the gate is for).
- Consequences: a backup from any launcher that writes this format, under any name, restores here; the gate stays absolute.

## ADR-037 The companion stand-in installs under the companion's own package
- Context: §14.3 asks for `CarouselFocusTest` with "the companion fake installed", and §5 puts the fakes in `:testkit` as a library. On a device a fake must be an installed app. The launcher reads the carousel at the fixed authority `HeroContract.AUTHORITY` and opens a title through the fixed component `HeroContract.DETAILS_ACTIVITY`, both inside `com.itsluminous.traktshelf`; Android lets one installed package own an authority, and a component name always names its own package. A fake under another id (`com.itsluminous.testkit.hero`) could neither be installed beside the real companion nor be the target of OK on the shelf.
- Decision (Phase 2 QA, 2026-11-09): `:testkit:hero` is an application module with `applicationId com.itsluminous.traktshelf` and namespace `com.itsluminous.verysmarttv.testkit.hero`. It holds one component, `FixtureHeroProvider` (`FakeHeroProvider` seeded with `HeroFixture` on create), declares `READ_HERO` at `signature` level exactly as the companion does, and is debug-only. `:launcher:connectedDebugAndroidTest` depends on its `installDebug`: on a test emulator it replaces the companion's debug build (same debug key, so `adb install -r` keeps the companion's data) until `./gradlew :traktshelf:installDebug` puts the real one back. The OK intent is checked in-process with an `Instrumentation.ActivityMonitor` (`support/IntentCapture`), which records and blocks the start, so the stand-in needs no activity and the test adds no library. The seventh TV app the focus tests switch on and off is `:testkit:tiles` (its own package: Android 14's shell can enable or disable whole packages only, not one alias of the test APK, and the launcher's uid may not touch another package's components); Tiles 1 to 6 are leanback aliases of the launcher's test APK.
- Rejected: a fake under its own package (cannot satisfy either fixed name); Espresso-Intents (a new catalog entry for what the framework's monitor already does); `pm uninstall` of the real companion before each run (loses nothing with `-k`, but the stand-in under the real id needs no uninstall at all); one dummy module with product flavours for several tile packages (`ci` names `lintDebug` per module, which flavours remove).
- Consequences: `HeroHandshakeTest` (§14.3, the real companion) and `CarouselFocusTest` cannot run in one install; a later phase runs them in two Gradle invocations or seeds the real companion through a test-only intent and drops the stand-in. A test emulator shows "Trakt shelf (test stand-in)" under Settings > Apps while it holds the stand-in.

## ADR-038 Where the §8 decomposition departed from the table
- Context: §8 lists the controllers and the methods each carries, with four rules; the move (Phase 2 coder, 2026-11-09) kept every body but could not keep every row of the table and still obey rule 1 ("no controller reaches into another's views") or compile between commits.
- Decision, as landed:
  - The sub-package move (§5) went first, before any controller, with the activity still whole: the members the packages now share across each other became public once, instead of twice. Every newly public signature carries `@NonNull`/`@Nullable` (lint's `UnknownNullness`, 187 findings fixed, none baselined); three `LambdaLast` findings on Java-only signatures are suppressed in place with the reason.
  - `HomeHost` names the controllers the others call (`grid()`, `shelf()`, `topBar()`, ...; `AmbientGlow`, `KeyDispatcher` and `IdleClock` are the activity's alone and have no accessor) besides the activity, state, handler, density, RTL, `open` and `findViewById`; controllers take the interface and reach the Context through `activity()`. Popups anchored to a pill ask `TopBarController.settingsPill()`/`inputsAnchor()` rather than finding the bar's views by id (rule 1). `HomeState` also holds the lifecycle flags (`started`, `stopped`, `resumed`, `tilesReady`), which as many methods read as the theme flags.
  - `refitGlass`, `hideGlass`, `applyTileNames`, `gridTopInRoot` and `focusLibrary` live in `grid.GridController`, not in `AmbientGlow`, `ShelfController` and `TopBarController` as the table says: each acts on the glass or the grid's RecyclerView, which the grid owns. `showGlowOnly` is split at the same seam: the shelf's half in `ShelfController`, the glow's in `AmbientGlow`, which exposes one-line fade, alpha and dip-and-swap methods so the shelf never touches the ambient view.
  - `onTileLongPress`'s body is `menus.GlassPopups.showTileMenu` (it builds a popup); the activity's `TileListener` method delegates to it, as the others delegate to the grid.
  - `ShelfController` and `CarouselController` landed in one commit: they are two faces of the one hero group in `activity_main.xml` and read each other's views, so they share the `shelf` package and package-private fields. `GlassPopups` builds the top menu from `InputsMenu.addInputRow`, as the table places it.
  - Fields read by anonymous listeners and receivers inside a controller are package-private, which removes the `SyntheticAccessor` warnings the fork had baselined for them (baseline 411 → 289 over the phase, nothing added; 2 `ApplySharedPref` entries moved with their `commit()` calls into `SettingsChoices`).
  - `grid.FocusRules` takes `(position, keyCode, Grid{count, columns, dockFilled, lastFocusable, libraryAtEnd, rtl, singleRow})` and returns `PASS`/`SWALLOW`/`LIBRARY`/`MOVE(target)`; `uniformRows` is not an input because today's rule never reads it. `topbar.TopBarFocus` carries the pre-pill rules with `Stop` an enum (`STAY`, `FRAMEWORK`, `GRID`, `CAROUSEL`, `PILL`) that Phase 3 extends by `SCORE_PILL`. `inputs.InputRows` takes a list of `Input`s built from `TvInputInfo` and a state lookup, so `TvInputManager.getInputState` is still asked only for the rows that show a state.
- Rejected: controllers typed on `HomeActivity` (a cycle between every package and `home`, and no fake host for JVM tests later); keeping the glass methods in `AmbientGlow` (two owners for one view); a `grid.GlassHighlight` class (one more class than the table, for a split the grid did not need).
- Consequences: `HomeActivity` is 465 lines of wiring; every file in `:launcher` is under 1,000 lines and the `fileLength` allowlist is gone; the 24 Espresso cases of ADR-020 stayed green through every commit of the split.

## ADR-039 Where the `:livescore` companion departed from §13
- Context: §12.2, §13 and §14.2 fixed the companion's behaviour before any ESPN payload had been parsed in code; the Phase 4 coder (2026-11-09) kept every rule but a few needed a decision the design did not make.
- Decisions, as landed:
  - **No RecyclerView.** §5.1 says "Views + RecyclerView everywhere"; every list on the companion's screens is under 40 rows (ADR-034), so they are `LinearLayout`s in a `ScrollView`, and the module has no library but `:core` and the stdlib AGP adds. The APK stays smaller and the D-pad focus order is the layout order, with nothing recycled under the focus.
  - **Football is fetched per day.** The bare `soccer/<league>/scoreboard` URL answers ESPN's own current day (2026-11-08 when asked on the evening of the 9th, IST) and refuses a date range; the companion asks for `?dates=<today>` on a live refresh and today plus tomorrow on a full one. F1 and tennis accept a range and get yesterday to tomorrow in one fetch.
  - **A final's `end_ms` is when the cache first saw it final.** ESPN's cricket `endDate` is the fixture's last scheduled day at 23:59 and its F1 `endDate` the race start; neither is the end. `EventCache.merge` keeps the first fetch time that found the event final (never later than now), so the pill's "final within 6 h" counts from the real end, and a match that was already over when the companion first fetched shows for 6 h from that fetch.
  - **The feed has no lap total.** The F1 scoreboard gives the current lap as `status.period` and no race length, so the live line is `F1 · São Paulo GP · Lap 32 · VER leads`, not `Lap 32/57`.
  - **`FakeSource` lives in `livescore/src/test`, not `:testkit`.** `:testkit` is a Java library the launcher's tests consume; the `Event` model is Kotlin inside the app module, which a library cannot depend on. The launcher's tests use `FakeScoreProvider` (already in `:testkit`), which speaks the contract and needs no model.
  - **Fixtures live under `livescore/src/test/resources/fixtures/<sport>/`** (the owner's Phase 4 instruction), recorded by `tools/dev/record_fixtures.sh` with every `events[]` cut to its first three entries and a `_note` saying so; the catalogue the picker offers (`res/raw/espn_catalogue.json`) is written by the same script from ESPN's `teams` endpoints plus a hand-kept cricket, F1 and tennis section.
  - **Settings** are Refresh now, Live refresh (on: the 60 s read-triggered fetch; off: only the 6 h job), Sports shown, Restore default follows and Clear follows: the owner's instruction named refresh behaviour and sports shown, which §13.6 did not list. A sport that is not shown is left out of Home, the picker, the pill and the fetch plan.
  - **No extra in-process timer while the launcher reads.** The launcher's own 60 s read of `/pill` while live is the timer (ADR-014); the companion only decides, on each read, whether that read fetches. Its own screens tick themselves (Home every 60 s through the same path, the scoreboard every 30 s).
  - **`ScoreContract.ACTION_OPEN`** was added to `:core` (a constant only): the action form of opening the companion at an event, for a launcher that prefers an action to a component name; `MainActivity` answers it and forwards to the scoreboard when an `event_id` is given.
  - **Memory on `HikViewer_TV_1GB`** reads 45 MB PSS with Home open and 47 MB cached in the background (Java heap 6 MB, native 3 to 12 MB, code 4 MB, shared system 15 MB, the rest swap-counted on a zram device); on the same AVD the launcher idles at 47 MB and traktshelf opens at 73 MB. The §13.5 targets (12 / 25 MB) were written for the real TV and are re-measured there in Phase 6; the companion holds the parsed events, a `JsonReader` while parsing and no bitmap, as §13.5 asks.
  - **Re-measured by own data (2026-11-10, same AVD, `dumpsys meminfo`, Private Dirty + swapped-out dirty, the companion's own pages; TOTAL PSS also counts mapped code and the shared system pages every process shows).** Idle in the background right after the launcher read `/pill`: 1.4 MB Private Dirty resident + 13.4 MB dirty in zram = **14.8 MB own data**; Java heap 2.8 MB allocated of a 5.5 MB heap; TOTAL PSS 19.2 MB. `ScoreboardActivity` open on a live match for 12 s: 16.9 MB Private Dirty + 6.6 MB swapped = **23.5 MB own data**; Java heap 2.8 MB allocated (unchanged: nothing is retained between the two states, no bitmap); native heap 12.3 MB private dirty, which on this AVD is the software renderer's; TOTAL PSS 65.9 MB, 28.2 MB of it Private Clean (code and `.so`/`.jar` maps the system shares). The §13.5 targets (12 MB idle, 25 MB open) are read against own data: open is within; idle is over by the runtime's own swapped pages (`.art`, `Dalvik Other`), not by anything the companion holds, and the real-TV pass decides whether 12 MB was the right figure for an ART process at all. No code change: the heap is flat between idle and open.
- Rejected: fetching football without a date (shows yesterday's results until ESPN's day turns); taking the feed's `endDate` as the end (a Test would show as "final" in the pill for days); a `FakeSource` in `:testkit` written against a duplicate Java model (two models to keep in step).
- Consequences: the JVM suite covers the parsers against the recorded and the hand-made fixtures (rain delay, super over, abandoned, tie, walkover, red flag); the provider's permission refusal is checked on the emulator with the shell user as the foreign caller; the §13.5 memory numbers are reported against the launcher's own on the same AVD until the real-TV pass.


## ADR-040 Where the Phase 3 launcher work departed from §9 and §10
- Context: §9 and §10 fixed the bars, the pill and the settings row before the views existed; the Phase 3 coder (2026-11-09) kept every rule but five details needed a decision the design did not make, and the Phase 3–4 review (same day) recorded them.
- Decisions, as landed:
  - **The score pill is a child of the root `FrameLayout`, not of the header row.** §9.2 says the layout above must not move when the pill hides; as a header child it would also have moved the grid under it by 24 dp every time a match ended. `ScorePillController` places it after every layout of `topButtons`: end-aligned with the last pill, 8 dp below the row, mirrored for RTL. Nothing above or below it is laid out against it.
  - **`Gb` keeps one decimal up to 100 GB**, whole from 100 GB ("1.1 GB free", "21.6 GB free", "10.0 GB free" for 9.95 GB). §9.1 says "one decimal under 10 GB, none above" and in the same paragraph names the reference image's "21.6 GB free"; the image wins, as it is what the owner asked to see. MB and B are whole.
  - **`Gb` lives in `launcher.topbar`, not `core.text`** (§5, §14.2 placed it in `:core`). Phases 3 and 4 ran in parallel on `:core` with a contract-constants-only rule; the one caller is the launcher's `ResourceBars`, so the class and `GbTest` sit beside it. It moves to `:core` the day a second module needs it.
  - **Back on a round pill returns to the grid** (rule 6). Phase 2 let Back on a pill fall through to the activity, where `back_opens_clock` could fire; with the bar consuming Back, that key opens the clock from the grid only.
  - **The Live scores subtitle reads "Scores app not installed"**: the companion's label is "Scores" (its module card), and the Trakt row names its app the same way ("Trakt shelf app not installed"); §10's "LiveScore app" was the working name.
  - **`ScoreProvider.call()` checks `WRITE_SCORES` itself.** The framework enforces a provider's read or write permission on `query`, `insert`, `update` and `delete`, but `call()` is reached by any caller holding either permission; §12.2 wants restore limited to the holder of the write permission, so the provider throws `SecurityException` when `checkCallingOrSelfPermission(WRITE_SCORES)` is not granted. A Robolectric case covers the refusal; on the device the shell user is refused before the call reaches the provider (it holds neither permission).
- Rejected: a header-row pill that is `INVISIBLE` rather than `GONE` (keeps the grid still but leaves a 24 dp hole whenever there is no match, which is most of the time); "22 GB free" to satisfy the §9.1 words (loses the figure the image shows); moving `Gb` to `:core` mid-phase (a `:core` change while the companion's coder was building against it).
- Consequences: `ScorePill`'s position is code, not XML (`ScorePillController.place`), and `HomeFocusTest` checks it end-aligns with the bar; `GbTest` is a launcher JVM test; the clock no longer opens from a focused pill with Back; a self-built companion signed with another key refuses the launcher's restore the same way it refuses its reads.

## ADR-041 The score pill stacks up to `score_rows` events, and the companion publishes every candidate (**amended** 2026-11-10: two rows by default)
- Context: §9.2 gave the pill one line, the companion's `PillChooser.choose`, which turns two live matches every 20 s. The owner asked (2026-11-10) for up to a configurable number of followed events stacked under the top-right pills, each on its own shade, the stack one focus stop; and for the two companions' banners to carry their names.
- Decisions:
  - **`/pill` returns one row per eligible event, ranked; the launcher cuts.** `PillChooser.ranked` is `choose()` first (so a one-line pill, and row 0 of any stack, behave exactly as before, alternation included) then every other eligible event by the existing rule (live > break > upcoming within 12 h > final within 6 h; follow reason, then earliest start). The contract gains `ScoreContract.MAX_ROWS` (5) and no `limit` parameter: the companion never needs to know a launcher's row count, and a launcher that reads one row reads row 0 (§12.2 "exactly one" becomes "one or more; exactly one `none` row when nothing is in the window"). The owner's "most recently changed first" among live events is not implemented: one fetch per competition gives every event of a competition one `updated_ms`, so the order would be fetch order, not change order; the existing reason-then-start rule stands.
  - **The launcher keeps the lines in place while the companion only turns its first row.** `ScoreLine.stack(previous, fresh, rows)` cuts to `score_rows` (held to 1..5) and, when the kept rows are the same events in the same states as the lines shown, keeps the previous order; any real change (an event gone, arrived, or in another state) takes the companion's order again. Without this, two live matches in a three-line stack would swap places every 20 s; with it a one-line pill still alternates, because one line is never "the same two events".
  - **`score_rows` is a theme key and a settings row.** Theme key `score_rows` (1 to 5, default 3 in rc1 and **2 from rc2**, amended 2026-11-10 at the owner's request: two lines sit under the pills without reaching the carousel's title at any hero_height; `config.xml`, both shipped themes), the **Live score rows** row right after **Live scores** in the panel (picker 1 to 5; the row shows the count in force, the theme's until a choice is saved), stored under `SettingsChoices.SCORE_ROWS_KEY`, cleared by a theme push and by Restore like every other choice, carried by Backup with the rest of `launcher_settings`.
  - **One stop, `row` inside it.** `TopBarFocus.Bar` carries `scoreRows` (0 while hidden; `scorePillShown` is derived), `Verdict` a `row`, and `onScorePillKey(key, row, bar, carousel)` walks the lines (rule 8, §9.3): Up from the grid or the carousel lands on the bottom line, Up from the top line reaches Inputs, Down from the bottom line leaves. `ScorePill` is a vertical `LinearLayout` of `ScoreLineView`s (the former `ScorePill` `TextView`, inflated from `score_line.xml`), each focusable with the glass ring of `score_line_bg`; at rest a line sits on a 10 % white rounded shade, the same whether or not the carousel's backdrop is behind it (ADR-048; until then a darker `score_line_bg_over_art` over a backdrop). OK on a line opens that line's event; the long press to the follow picker stays on every line, as §9.2 asks.
  - **The flaky OK test was the key injection, not the pill.** Espresso's `pressKey` injects ACTION_DOWN and ACTION_UP as two events with the main looper idled between them; on the 1 GB emulator under a connected run that gap passed the 500 ms long-press timeout now and then, and OK on the pill opened the follow picker (one intent, the wrong component). `HomeTestRule.tap` dispatches both events to the activity in one main-thread turn, so no posted long-press check can run between them; the test asserts one intent and waits a long-press timeout for a second. The long-press listener stays because §9.2 requires it.
  - **Banners are a layer-list of a vector and a text bitmap.** Android drawables cannot draw text, so `res/drawable/banner.xml` layers `banner_art.xml` (the slate, the diagonal, the 90 dp disc raised to leave room) and `res/mipmap-xhdpi/banner.png` (320×180 px, transparent, the name in Outfit 500 at 28 px, rendered by the committed `tools/dev/render_banner.py` from the launcher's `outfit.ttf`; `--check` fails when the PNG is stale). The artwork is full-bleed: the launcher's tile rounds every banner's corners itself, and transparent corners would read as black holes in other launchers. `icon.xml` and the module-card labels are unchanged.
- Rejected: a `limit` query parameter on `/pill` (the contract would carry a launcher concern, and every reader would have to pass it); alternation turned off whenever the companion has two rows to give (a one-line launcher would then show one of two live matches for good); removing the long press from the pill (§9.2 names it); `UiDevice.pressKeyCode` for the OK test (UiAutomator's injection goes through the system and is no more bounded than Espresso's under load); the whole banner as one PNG (the icon would then live in two places).
- Consequences: `ScoreFeed.Listener.onPill` takes a `List<Row>` (empty for none), `TopBarFocusTest`'s bar takes a row count, `ScorePillTest` covers the stack and the line, `ScoreLineTest` the cut and the hold, `HomeFocusTest` the 1-, 3- and 5-line stacks against `ScoreFixture.STACK` (five events, two of them live, in the `:testkit:score` stand-in); `PillChooserTest` and `ScoreProviderTest` cover `ranked` and the multi-row cursor. The frosted and default themes carry `"score_rows": 2` (3 until rc2).

## ADR-042 A sport icon on every score line, from the contract's `sport` value set
- Context: with the stack (ADR-041) a Home can show five lines from several sports at once, and only the kicker and the companion's text tell a cricket Test from a football match. The owner asked (2026-11-10) for a small icon per line, bundled in the launcher, chosen by the row's `sport` column.
- Decisions:
  - **`ScoreContract.SPORTS` is the value set.** `:core` gains `SPORT_BADMINTON` and `SPORT_HOCKEY` beside the five it had, and `SPORTS`, the array a reader iterates. The companion publishes the four it has a source for (`Sport` in `:livescore`, each token checked against `SPORTS` by `SportTest`); a value outside the set is not an error, it gets the generic icon, so a companion may add a sport before the launcher learns it.
  - **Eight hand-drawn vectors, one map.** `ic_sport_cricket` (bat and ball), `_football` (pentagon and seams), `_f1` (chequered flag), `_tennis` (racket and ball), `_badminton` (shuttlecock), `_basketball` (seams), `_hockey` (stick and ball), `_other` (a trophy): 24 dp outlines, stroke 1.8, white at 85 % in the path itself (`#D9FFFFFF`), each under 800 bytes, original work, no icon set copied. `topbar.SportIcons.forSport(String)` is a pure switch to a `@DrawableRes`, `nameOf` the matching `@StringRes` (`sport_cricket` … `sport_other`); `SportIconsTest` checks every `SPORTS` value maps to its own icon and name, never the fallback, and that null, empty, another case or an unknown sport gets the trophy.
  - **The icon is a view at the line's end, inside the shade.** `ScoreLineView` was a `TextView`; it is now a horizontal `LinearLayout` (the focus stop, the shade, the ring, the content description) holding the `TextView` (dot, kicker, line, 500 dp at most) and a 16 dp `ImageView` 7 dp after it, inflated from `score_line_content.xml` with `<merge>` so `new ScoreLineView(ctx)` and the layout inflation build the same row. The icon's tag is the drawable's entry name (`"ic_sport_cricket"`), so a device test can say which icon a line shows without reading pixels; both children are `importantForAccessibility="no"` and the row's description is `score_line_description`: kicker, line, a full stop, the sport's name ("LIVE T20I · AFG 19/4 (6) v ZIM. Cricket").
  - **The sport rides through the launcher as data.** `ScoreFeed.Row.sport` (empty when the column is missing), `ScoreLine.Text.sport` (trimmed, empty for null; `of` takes it after the event id), nothing else changes; the launcher still does no sports logic.
  - **The stand-in's stack carries three sports.** `ScoreFixture.STACK` row 1 is now a tennis match (`ATP Finals · Alcaraz 6–4 3–2 Sinner`), so cricket, tennis and football are all on screen in `HomeFocusTest.rule8_fiveRows`, which asserts each line's icon is visible, last in the row, inside the shade, tagged for its row's sport (`STACK_SPORTS`), and that the description ends in the sport.
- Rejected: a compound drawable on the `TextView` (no icon view to assert, and the owner asked for one); tinting in the `ImageView` (`android:tint` wants AppCompat's `app:tint` under lint; the colour belongs to the vector anyway, it is used nowhere else); a `switch` on the companion's `Sport` enum (the launcher cannot see Kotlin in `:livescore`, and the contract is the one place both sides read); adding `BASKETBALL`, `BADMINTON` and `HOCKEY` to the companion's enum (nothing fetches them; the contract documents the set, the companion emits what it has).
- Consequences: `ScorePillTest` reads the text child for the span, dot and colour and the icon child for the tag; `HomeTestRule.scoreLines` and `HomeFocusTest` read `ScoreLineView.text()`; a sport the companion adds later needs one vector, one string and two `case`s in the launcher, with `SportIconsTest` failing until it has them.

## ADR-043 Where the Phase 5 setup tool departed from §16 and §17
- Context: §16.1 planned the setup package on `adb-shell`, `rsa` and `zeroconf`; the owner asked (2026-11-10) for stock Python 3.9+ with `cryptography` alone, and for an install that grants nothing. The carried shell tooling also held rules §17.3 did not list, and one of §17.3's sentences would have refused the owner's own list.
- Decisions:
  - **One dependency; the ADB protocol and mDNS are written here.** `setup/verysmarttv_setup/adb/` speaks the wire protocol on a plain socket (CNXN, AUTH token → PKCS#1 v1.5 signature over the 20-byte token as `Prehashed(SHA1)` → the public key in Android's `RSAPublicKey` layout when no key is trusted, OPEN/WRTE/OKAY/CLSE streams, the `sync:` SEND/RECV service for push and pull, `reboot:`), with base64 chunks over `shell:` as the fallback a sync refusal falls to. `discover.py` sends one UDP query to 224.0.0.251:5353 for `_adb-tls-connect._tcp` and `_adb._tcp` and parses the answers (PTR, SRV, A, name compression), then scans the /24 for port 5555 with 64 threads. `requirements.txt` pins `cryptography` only. The optional Google-adb backend (`NativeAdbDevice`) is not carried: Chromecast-class devices pair with Google's adb once and `adb tcpip 5555`, which this client then reaches; the install flow says so when a port answers STLS.
  - **The install grants nothing.** No `pm grant` (the fork granted `ACCESS_FINE_LOCATION` for the Wi-Fi name in the network pill) and no accessibility helpers or `WRITE_SECURE_SETTINGS`; the launcher asks for what it needs itself, and the helper switches stay a TV-side setting. `cmd package compile -m speed -f` is kept (a 1 GB TV's first Home is faster for it). The stock launcher is **left enabled by default**, as §16.2's step 4 shows, and disabled only on a yes (`--disable-stock`), only after VerySmartTV answers HOME, with the rollback and the handover file of the fork's script.
  - **Factory and test packages: never started, but a list may disable them, and the user is told the impact first.** §17.3's "never touching `*factory*`/`*hkcfac*`" is read as the AGENTS rule it comes from (never start one, never hand Home to one: `homeguard.FACTORY_RE` keeps them out of the launchers that count and out of any `am start`). The owner's own list `xiaomi-mi-tv-4a-mooq1` disables `com.duokan.factorytest` on purpose, the factory-test HOME claimant, and refusing it would refuse that list. Amended in Phase 6 (the review's advisory, accepted by the owner 2026-11-10): when a plan holds a package matching `lists.FACTORY_RE` (`factory|hkcfac`, case-insensitive), `cli.confirm_list` prints a warning block before the question naming each one, what they are (the maker's factory-test, service-menu and board self-test apps), that the TV's factory/service menu and some board self-tests stop working until they are enabled again, and that `setup restore` re-enables them; the question then needs a typed yes, `--yes` included, and a non-interactive run says so and applies nothing. `--dry-run` prints the same block.
  - **The input-driver and handler guards are carried too.** `disable.sh`'s `TV_INPUT_HARDWARE` check (requested or granted permission block, the Service Resolver Table on Lollipop, the hung-watchdog and no-block readings, fail closed) and its "which app opens the inputs / Settings" queries are in `debloat.safety_checks`, off-switches `--allow-input-drivers` / `--allow-handlers`; §17.3 listed only the Home guard, setupwraith, core and the record, but a black HDMI port is the one thing the owner cannot fix from the couch.
  - **Batches follow the list.** A list with `# ---- Batch N` sections is applied section by section (the owner's lists are written that way); one without is applied in groups of eight. Between batches: `resolve-activity` must still name a launcher (else the run stops and says how to undo), and a screenshot goes to `~/.verysmarttv/shots/`.
  - **Records live under `~/.verysmarttv/records/`, keyed by TV and list** (ADR-028: `sha256(serial + model)[:12]`, plus the list path's digest), with the fork's first-record-wins, extend-on-edit and chooser/not-a-launcher readings.
  - **Headers verbatim except Apply/Undo** (§17.1), rewritten by the carry to `setup debloat --preset <slug>` / `setup restore --preset <slug> [--stock <package>]`; the two lists whose Apply/Undo lines say "NOT tools/disable.sh" (firmware that denies `pm disable-user`) keep their text. The stock launcher an Undo line named goes into `index.json` as `stock_launcher`.
  - **The tool's own text does not name the upstream project**: the identifier gate forbids it outside the licence, notices, README, docs and presets, so the suggestion says "a community list (MIT; presets/README.md names the source)"; `presets/README.md` carries the CleanYourTV MIT notice (ADR-029).
  - **Subcommand names** are the owner's: `setup`, `discover`, `probe`, `install`, `theme`, `debloat`, `restore`, `check`, `screenshot`, `adb-closed` (§16.1's `find`, `guide`, `fetch`, `close-adb` fold into `discover`, the hints `setup` prints when nothing answers, `install`'s release step and `adb-closed`). `backup` is not a subcommand: the launcher's own Backup & restore panel and `content read --uri content://com.itsluminous.verysmarttv.backup/settings` cover it, and the old-launcher migration of ADR-010 is the panel's Import row.
  - **Tier ranking adds "identifiers in common"**: within a tier, a preset whose tokens also hold the TV's firmware build id, board or product ranks first, so the Mi TV 4A (model `MiTV-MOOQ1`, device `tarzan`, `QTG3.200305.006.2591`) suggests `xiaomi-mi-tv-4a-mooq1` over `xiaomi-mi-tv-4a`, which shares model and codename.
- Rejected: `adb-shell` (another three packages, its own TLS gap, and a 0.4.x API this tool uses a tenth of); `zeroconf` (a dependency for one two-second query); refusing factory packages in lists (breaks the owner's list); disabling the stock launcher without asking (the fork did; §16.2 asks); granting location at install (the owner said grant nothing).
- Consequences: `tools/dev/push_theme.py` is removed (`setup theme` replaces it, `docs/themes.md` updated); 83 Python tests under `setup/tests/` with a fake TV and a fake adbd; `ci.yml` gains `setup-tests` (ubuntu + windows, Python 3.9 and 3.12, plus `build_presets_index.py --check`); `THIRD_PARTY_NOTICES.md` names `cryptography` and the carried tooling.

## ADR-044 Badminton from SportMicro's "Badminton Micro" API through RapidAPI, with the user's own key (**amended** 2026-11-10: the key is asked for on the first badminton follow; fetched at most every 5 minutes)
- Context: the owner asked (2026-11-10) for badminton in the Scores companion. ESPN has no badminton feed (`site.api.espn.com/apis/site/v2/sports/badminton/scoreboard` → 404), so a second `ScoreSource` was needed, and §13.1's criteria (no key or a free key the user makes; terms that allow personal use; live match state and game scores for the BWF World Tour at least; a cadence that fits 60 s polling; stability) were run over the candidates with curl the same day; the table is in §13.1.
- Decisions:
  - **No keyless source is viable, so the source is keyed and the key is the user's.** BWF's own site and its JSON sit behind a Cloudflare JavaScript challenge on every URL (403, `cf-mitigated: challenge`), which a TV's `HttpURLConnection` cannot pass; BWF Tournament Software is a login wall whose terms forbid automated use; Sofascore answers 403 to any non-browser; LiveScore.com has no badminton (410); TheSportsDB lists a tournament as one event a day with no matches; API-Sports and AllSportsAPI have no badminton product. Flashscore's hidden feed answers in full (match state, games, points, 77 KB for the day) but its terms forbid automated requests and scraping in those words, and §13.1's "ToS allows personal use" criterion is what separates it from ESPN's undocumented feeds, so it is rejected even though it is the one keyless feed that has the data. SportMicro's "Badminton Micro" on RapidAPI (`badminton-micro.p.rapidapi.com`, `rapidapi.com/sportmicro-sportmicro-default/api/badminton-micro`; the listing this ADR first named "SportDevs' Badminton Devs" is the same vendor's API under its current name, renamed here on 2026-11-10 with the first recording) has the data (status, games won, points per game, tournament, league) under RapidAPI's terms with a free plan, so it is the source; the user creates the key and enters it in **Settings → Badminton data key (RapidAPI · Badminton Micro)**, where it is stored in the companion's `SharedPreferences`, trimmed, never in the APK, a backup (`/backup` carries follows only) or a log (the Settings row shows "Not set" or the key's last four characters). **The key is the user's own and only ever user-entered on the TV**: never a GitHub secret, a `BuildConfig` field, a Gradle property or a CI variable, and the row and `docs/providers.md` say that the key may cost the user money beyond the free tier.
  - **Without a key badminton is listed, not fetched.** `SportMicroSource.scoreboard` answers an empty list and logs once when the key is empty, so a badminton follow costs no request and no failure backoff; the picker's Badminton column shows "Badminton scores need a data key" in place of tournaments.
  - **The key is asked for the moment badminton is enabled** (amended 2026-11-10, at the owner's request). `BadmintonGate.needsKey(follows, key)` (pure) is true when the follows include badminton and no key is stored; `FollowActivity` runs every OK through it with the change it is about to make (a leaf's toggle, a section's select-all), so ticking the Badminton sport, a tournament, a player or a match with no key opens `BadmintonKeyDialog` first: a text field for the TV's keyboard, a message that the key is the user's own RapidAPI key for SportMicro's Badminton Micro API, kept on the TV, 100 requests a day on the free plan and possibly billed beyond it; OK (or the keyboard's Done key, since the TV keyboard covers the buttons) saves the key and lets the follow land, Cancel leaves badminton unfollowed and the boxes as they were. The same dialog is Settings' **Badminton data key** row, with Remove added; the row shows "Not set" or the key's last four characters (`BadmintonGate.tail`). Removing the key keeps every follow: the companion's Home then shows a "Badminton scores need a data key" row above the events (OK opens the dialog), the picker's column says the same, and `SportMicroSource` fetches nothing. The key is never printed, logged or backed up.
  - **One registry, one source per sport.** `Sources.create` builds a `SourceRegistry` of `EspnSource` (cricket, football, F1, tennis; its `sports()` no longer says every sport) and `SportMicroSource` (badminton), and the registry routes each sport to the first source that claims it; `ScoreRepo`, the picker and the provider still see one `ScoreSource`. `HttpClient.stream` gained a headers argument for RapidAPI's `x-rapidapi-key` and `x-rapidapi-host`.
  - **Badminton is a day-wide feed like the cricket scorepanel.** `Sport.oneFetchPerDay` marks both; `FetchKey.of` gives them no competition, `RefreshPolicy.fullPlan` adds one key for any badminton follow, and the repo asks `matches-by-date` for today on a live refresh and today plus tomorrow on a full one (like football). **Badminton is fetched at most every 5 minutes** (`RefreshPolicy.BADMINTON_LIVE_MS`; the other sports keep 60 s): the free plan answers `x-ratelimit-requests-limit: 100` with a daily reset (`x-ratelimit-requests-reset` ≈ 86 400 s, measured 2026-11-10 against the owner's key), and 100 requests a day is 1 h 40 min of 60 s polling but about 8 hours of a live match at 5 min plus the 6 h job's two days. So `RefreshPolicy.liveIntervalMs(sport)` and `liveReadMs(sport)` are per sport (`isStale` follows: a badminton row is stale after 10 min), and `ScoreRepo.refreshOne` reads the cache instead of fetching when the key's last fetch is younger than `minFetchGapMs(sport)`, so the open scoreboard's 30 s timer cannot shorten it. The Settings row says "fetched at most every 5 min" and names the 100 a day; the feed answers 429 when the quota runs out and the existing backoff and `stale` handle it.
  - **The feed has no static catalogue, so the picker reads the cache.** `SportMicroSource.competitions` and `teams` are empty (the vendor's tournament ids are not knowable offline); `FollowActivity` lists, for a sport whose source has no catalogue, the tournaments of the cached window (soonest first) and under one its players (from the sides of its matches) and "Match · …" rows, fetching the sport once (`ScoreRepo.refreshSport`) when the cache holds none of it. A badminton competition follow therefore names a tournament of the week; "All Badminton" is the lasting follow. ESPN's sports are unchanged: the cache is consulted only when the catalogue is empty.
  - **Lines mirror tennis.** `Japan Masters · Sindhu 21-18 11-9 Axelsen`, games where tennis has sets, the tournament cut first; a pair by surnames (`Chang / Yang`) or, when the surnames alone exceed 48 characters, by abbreviations (`CHA/YAN`); a walkover `Antonsen w/o Christie` (winner first), a retirement `… Antonsen ret.`; the break kicker is the pause word (`INTERVAL`), read from the last ` · ` part of `status_detail` (so a tennis `Quarterfinal · Suspended` now reads `SUSPENDED`, not `QUARTERFINAL`). The parser reads the surname first when the feed writes initials after it, with or without dots (`Matsuta N.`, `Pong L K K`, `He Z-W`), last otherwise (`Victor Lai`).
  - **States.** `StateNormaliser` reads SportMicro's words beside ESPN's letters (§13.4): endings (`walkover`, `retired`, `canceled`, `postponed`) as a type or a reason are `final` with the word kept; pauses (`interrupted`, `suspended`, `delayed`, `Interval`) are `break`; and the parser calls the gap after a finished game with no next game started the interval (21 with a two-point lead, or 30), whatever game ordinal the reason names, unless the reason is itself a pause or ending. The recorded day showed a retirement reported as plain `finished` / `Ended` with the second game at 19-8 and the games 1-0, so the winner is read from the games-won numbers first and from the points only when the feed gives none.
  - **Fixtures are recorded** (2026-11-10, the owner's key, 10 requests). The schema `matches-by-date` answers, the one the source reads, is an array of `{date, matches[]}` day groups whose matches are **flat**: `id`, `name` (`Matsuta N. vs Kantemyr Y.`), `status` (a word: `upcoming`, `finished`, `canceled`; the vendor documents `live`), `status_reason` (`Not started`, `Ended`, `Walkover`, `Canceled`), `start_time` (the session's start, often `00:00:00+00:00`), `specific_start_time` (the real first serve, once begun), `tournament_id` / `tournament_name` (`Kumamoto Masters Japan, WS, Qualifying`), `league_id` / `league_name` (`Kumamoto Masters Japan - WS`), `season_id` / `season_name`, `home_team_id` / `home_team_name` (a pair as `Pong L K K / Choi C`), `home_team_score` (the games won, a number, absent before play), `home_team_period_N_score` (the points of game N), `duration`, `tournament_importance`, `*_hash_image`; there is **no `round`**. `/matches?tournament_id=eq.<id>` (and `/matches-live`, empty when recorded) answers the **nested** shape: `status: {type, reason}` plus `status_type`, `home_team_score: {current, display, period_N}`, `times: {specific_start_time}`, `arena_name`, `last_period`. `SportMicroParser` reads both (`Score.read` for the object, `Score.readFlat` for the `home_team_*` names), prefers `specific_start_time`, and drops the league from the row's meta when the tournament already names it. `livescore/src/test/resources/fixtures/badminton/matches-20261110.json` (five of the day's 143 matches, one per status shape first) and `matches-nested-20261110.json` are the recordings, `edge-canceled.json` and `edge-ended-unfinished-game.json` are copied from the full recording, and `edge-live.json`, `edge-deciding-game.json`, `edge-between-games.json` and `edge-retired.json` are hand-made in the flat shape because no match was live when the day was recorded (their `_note` says so; the live reason words are a guess until a live day is recorded). `tools/dev/record_fixtures.sh --badminton [day]` records both shapes (two requests) with `RAPIDAPI_KEY` from the environment, strips the image hashes and keeps five matches per day with a `_note`; the key goes in a header, never in a file.
- Rejected: Flashscore's feed (terms); shipping a key in the APK or in the release secrets (one quota shared by every TV, and a secret in a public APK); a static badminton catalogue of guessed tournament ids (wrong the week it ships); fetching badminton without a key and backing off on the 403 (a follow would then cost a request a minute for nothing); a 60 s cadence for badminton like the other sports (first chosen; reversed on 2026-11-10 once the headers showed 100 requests a day: it would spend the day's quota in 1 h 40 min); `Sofascore`'s shape through a RapidAPI reseller (a scrape resold).
- Consequences: `Sport.BADMINTON` publishes `ScoreContract.SPORT_BADMINTON`, which the launcher's `SportIcons` already draws (ADR-042); the stand-in's `ScoreFixture.UPCOMING` row is now a badminton match (`Japan Masters · Sindhu v Axelsen`, `STACK_SPORTS[3]`), so four sports are on screen in `HomeFocusTest.rule8_fiveRows` and the badminton icon is exercised there; `Ui.sportName`, `LineFormatter`, `RefreshPolicy.fullPlan`, `ScoreRepo.fetchKey` and the test fakes gained the sport; `SportMicroParserTest`, `SportMicroSourceTest`, `SourceRegistryTest`, `PrefsTest` and new cases in `StateNormaliserTest`, `LineFormatterTest`, `RefreshPolicyTest`, `SportTest` cover it on the JVM, `FollowFlowTest` on the emulator (the key hint, the cached tournament and its players, a player follow reaching `/pill` with `sport=badminton`); `THIRD_PARTY_NOTICES.md` names SportMicro and RapidAPI; the first-run defaults (ADR-033) are unchanged, so badminton shows nothing until the user enters a key and follows something.

## ADR-045 Three-state boxes in the follow picker
- Context: the picker's rows (§13.6, ADR-034) each showed a ☐/☑ glyph for their own follow, so "Cricket" read as unticked while India and the IPL were followed under it, and the only way to follow or drop a whole section was its own row. The owner asked (2026-11-10) for an indeterminate box on a partly selected section, a tick on a fully selected one, an empty box on none, and for OK on a section to select all, then clear all.
- Decisions:
  - **The box is drawn, not a glyph.** `TriStateCheckView` draws a rounded square (empty), the square with a horizontal bar (`PARTIAL`) or a filled square with a tick (`ALL`), so every TV shows the same three shapes whatever its fonts; its content description is `check_none` / `check_partial` / `check_all` ("Not followed", "Partly followed", "Followed"), which is also what the Espresso test reads. The row keeps the focus; the box is not focusable.
  - **The rule, in a pure class.** `SelectionState.of(selected, total)`: none, some or all of the children (no children is an empty box); `ofChildren(selfFollowed, children)`: a section followed itself is ticked whatever its children (it covers them), else a tick when every child is ticked, a bar when any child is ticked or barred; `selectsAllOnOk(state)`: OK on anything but a full tick selects all, on a full tick clears all. `PickerSelection` reads the boxes off a follow list: a leaf from its own follow; a competition from its follow and its team and match follows; a sport from its follow and its competitions' boxes, and barred when a follow of that sport exists that no listed competition holds (a team of a league the catalogue does not list), so nothing followed hides behind an empty box.
  - **What OK does.** On a leaf, the toggle as before. On a section that is not fully ticked, **select all** adds the section's own follow (the sport or competition follow, which covers everything under it); the children's own follows are left as they are, and their boxes keep showing their own follows (a child under a ticked competition is not drawn ticked: the row's box says what that row's follow is, the parent's box says the section is covered). On a fully ticked competition, **clear all** removes its follow and every team and match follow under it; on a fully ticked sport, every follow of that sport whatever its kind. `FollowStore.replaceAll(remove, add)` applies a move as one save and one notification. "All cricket" in the competitions column is the sport follow as a leaf, so it ticks when the sport row does.
  - **Every visible box is recomputed after any OK**, parents and children alike (`refreshBoxes`): the lists are under 40 rows (ADR-034), and the follow list is in memory.
- Rejected: a parent follow that expands into child follows (a sport follow would become dozens of competition and team follows, the backup would carry them, and new competitions would not be covered); drawing a child ticked when its parent is followed (OK on it would then have to remove it from a parent that does not list it); Unicode glyphs for the three states (the TV's fallback font may lack the bar glyph, and the drawn square matches the rows' geometry); a drawable state list with a custom state attribute (more XML than the forty lines of drawing, and no place for the description).
- Consequences: `SelectionStateTest` (the count rule, the section rule, the OK rule, the view's descriptions), `PickerSelectionTest` (leaves, competitions, sports, stray follows, the two moves), a `FollowStoreTest` case for `replaceAll`; `FollowFlowTest` on the emulator walks one child → bar, every child → tick, OK on the tick → everything cleared, OK again → the competition followed with the children's boxes still empty, OK on the barred sport → the sport followed, OK again → every cricket follow gone. `tick_on` / `tick_off` are removed; `pick_row.xml` carries the view under the same `tick` id.

## ADR-047 The first release is 0.1.0; versionCode gains an epoch so the 1.0.0 candidates upgrade
- Context: three release candidates went out on 2026-11-10 as `v1.0.0-rc1`, `v1.0.0-rc2` and `v1.0.0-rc3`, each with `versionCode` 10000 (ADR-023's `X·10000+Y·100+Z` ignores the suffix). The owner then decided the first public release is **0.1.0**, not 1.0.0: a 0.x line says the provider contracts and theme keys may still move, and `1.0.0` is kept for the point they are promised stable (§15.4's semver meaning). Under the old scheme `0.1.0` is code 100, below the 10000 a TV with a candidate already holds, so Android would refuse the upgrade.
- Decision: `AppVersion.code = EPOCH + X·10000 + Y·100 + Z` with `EPOCH = 1000000`, so `0.1.0-rc1` and `0.1.0` are 1000100, `1.0.0` 1010000, `99.99.99` 1999999 (well under Android's limit). Every release code is above `LAST_PRE_EPOCH_CODE` (10000), the order of versions is the order of codes within the epoch, a candidate still shares its final's code (installed over it with `-r`), and the dev build stays `0.0.0-dev`/1. The three `v1.0.0-rc*` tags and release pages stay as published; `CHANGELOG.md` carries their contents under `[0.1.0-rc1]` as *(was 1.0.0-rcN)* sections with a renumbering note, and the setup tool reports `0.1.0-rc1`. `release.yml` is unchanged: its tag check already accepts `v0.1.0-rc1`; the comment in its header that quotes the old formula is for the owner to refresh, since workflows are not edited without their say-so.
- Rejected: re-tagging the candidates as 0.x (rewriting published tags and release pages); a one-off code for 0.1.0 (the next version would have to remember it); making the owner uninstall the candidates (the point of a candidate was to prove the upgrade path); keeping 1.0.0 (the owner's call on what 1.0.0 promises).
- Consequences: `AppVersionTest` covers the epoch, the pre-epoch ceiling and the order of a version sequence; a TV on `1.0.0-rc3` takes `0.1.0-rc1` (code 1000100 > 10000, same signing key). Anything that compares `versionCode` across the epoch boundary (nothing in the repository does) would see 0.1.0 above 1.0.0-rc3, which is the intent.

## ADR-049 An experimental badminton source that reads BWF's own Match Centre through a hidden WebView (off by default)
- Context: ADR-044 rejected BWF's own site because every URL answers `HttpURLConnection` with a Cloudflare JavaScript challenge (403, `cf-mitigated: challenge`), and §20.2 left "a WebView-based scraper for a source behind a browser challenge" as planned, not built. The owner asked for it on 2026-11-10 as an **experimental, off-by-default** option, knowing it is fragile. Probed the same evening on `HikViewer_TV_1GB` (Android 14, Android System WebView 156): the WebView loads `bwfbadminton.com/live/` with HTTP 200 and the title `Live | BWF Fansite`, no challenge page, no `cf_clearance` cookie needed; the fansite's `/live-scores/` and the World Tour site's `/tournament/<id>/.../live/` pages hold no scores themselves (their "LiveScore" link goes to `match-centre.bwfbadminton.com/<tmtId>`), and the `extranet-lv.bwfbadminton.com/api/vue-live-scores` and `vue-tournaments` URLs ADR-044 named are 404 from the page too. The **Match Centre** (`match-centre.bwfbadminton.com`, a Vue app) is what carries live scores: it polls `extranet-lv.bwfbadminton.com/api/match-center/vue-current-live` (the tournaments live this week), `vue-live-matches?tmtId=<id>&tmtType=0` (the matches on court now, every 20 s while one is live, 90 s otherwise), and per match `vue-live-single`, `vue-match-stat`, `vue-game-stat`, `vue-game-graph`. From the page's origin every one answered 200 with JSON.
- Decisions:
  - **A third `ScoreSource` for badminton, chosen by a preference.** `Prefs.badmintonSource` is `SPORTMICRO` (the default, ADR-044 unchanged), `BWF_WEBVIEW` or `NONE`; **Settings → Badminton source** offers *SportMicro (your RapidAPI key)*, *BWF website (experimental)* and *Off*, with a line under the experimental row saying it opens a hidden browser, uses more memory, needs no key and may stop working when the site changes. `SourceRegistry` takes an `enabled` predicate: `SportMicroSource` is enabled only under `SPORTMICRO`, `BwfWebViewSource` only under `BWF_WEBVIEW`, so under `NONE` no source claims badminton and the picker, Home, the pill and the fetch plan leave it out (`ScoreRepo.followed` keeps only the sports a source claims). The key gate (`BadmintonGate.needsKey`) asks for a key only under `SPORTMICRO`; the **Badminton data key** row shows only then. Nothing in `EspnSource`, the launcher or the provider contract changes.
  - **The page is loaded in one hidden `WebView`, created on the main thread for one fetch and destroyed after it.** `source/bwf/WebViewPageLoader` (the `BwfPageLoader` the source is given; tests inject a fake) posts to the main looper: a `WebView` over the application context with JavaScript on, DOM storage on, a desktop-less Android Chrome user agent (`Chrome/120`, the one the probe passed with; the default WebView string carries `; wv`), no `WebChromeClient`, never attached to a window, file and content URLs off (`allowFileAccess`, `allowContentAccess`: API 29 allows both by default), no location, no new windows. The view reaches only BWF's hosts and Cloudflare's challenge host (`WebViewPageLoader.allowed`: `bwfbadminton.com` and its subdomains, `challenges.cloudflare.com`): `shouldOverrideUrlLoading` refuses any other navigation and `shouldInterceptRequest` answers any other request with an empty 403 on the device, which on 2026-11-11 kept the page's `cdn.jsdelivr.net` icon font, Google Fonts, Cloudflare Insights and Google Tag Manager off the TV without changing what the page handed back. It loads `https://match-centre.bwfbadminton.com/` and, on `onPageFinished` of a page whose title is not Cloudflare's `Just a moment…` (and whose capture has not already failed: Chromium's own error page finishes too), evaluates one script that calls the page's own `fetch` for `vue-current-live` and then, one tournament at a time, `vue-live-matches` for every tournament it names (at most `MAX_TOURNAMENTS` = 4), with the page's default `same-origin` credentials (what its own axios calls send; a `credentials: 'include'` fetch would need CORS headers the API does not send), and hands the raw JSON strings to a `@JavascriptInterface` bridge (`LiveScoreBridge.tournaments`, `.matches(id, json)`, `.skipped(id, reason)`, `.done`, `.fail(reason)`), assembled by the pure `PendingCapture`. A tournament whose `vue-live-matches` fails the page's `fetch` is retried once after `RETRY_DELAY_MS` = 600 ms with a cache-busting `_=` parameter, then skipped; only every tournament failing fails the capture (reviewed 2026-11-11: the API's cached answer for some tournaments carried no CORS header, so the page's origin could not read it although it arrived with no HTTP error; the uncached re-fetch carried the header, and every tournament answered in every run tried; without the tolerance one such tournament failed the whole fetch). The fetch thread waits on a latch for `LOAD_TIMEOUT_MS` = 30 s; whatever the outcome, the main thread then calls `stopLoading`, `removeJavascriptInterface`, `loadUrl("about:blank")`, `clearCache(true)`, `destroy`, deletes the cookies and the WebStorage (`CookieManager.removeAllCookies`, `WebStorage.deleteAllData`: nothing from the session outlives the fetch), and calls `Application.onTrimMemory(TRIM_MEMORY_RUNNING_CRITICAL)`, which reaches the `ComponentCallbacks2` Chromium registers on the application and makes it purge its caches. `shouldInterceptRequest` is not used to read bodies: a body re-fetched with `HttpURLConnection` would meet the challenge again (the TLS fingerprint is the WebView's), and the page's own `fetch` carries the right cookies and origin.
  - **It runs only while a screen shows a score, never from the job.** `BwfWebViewSource.scoreboard` is called from `ScoreRepo`'s one fetch executor, on the same `RefreshPolicy` decisions as the other sources: a provider read while a followed badminton event is live (the launcher on screen, which reads only while Home is resumed), the open Scores screens and the full refresh from Settings. The JobScheduler job (the 6 h fixture refresh and the one-off before a start) calls `ScoreRepo.refreshInBackground`, which is `refreshAll` without the badminton key while the source is `BWF_WEBVIEW` (reviewed 2026-11-11: a hidden Chromium page is not loaded while the TV may be asleep; SportMicro's plain HTTP call still runs from the job as before). Badminton keeps `BADMINTON_LIVE_MS` = 5 min as its live cadence under this source too: not for a quota, but because a page load of Chromium on a 1 GB TV every minute is not what §13.5 means by a background companion; `Prefs.liveRefresh` off stops it like every other fetch. The two days of a full refresh share one page load: the source answers the second `scoreboard` call of a `REUSE_MS` = 60 s window from the last capture.
  - **Live matches only.** `vue-live-matches` lists the matches on court (warming up, playing, waiting between games, and the ones just finished while the page keeps them), not the day's order of play or results, so this source yields `live`, `break` and `final` events, and `upcoming` only for a match on court that has not begun (`Warm Up`), whose start is set to the fetch time (the day's start, the only time the feed gives, read as a 05:30 kicker on the emulator); the one-off job 2 min before a start has nothing to key on. The parser (`BwfParser`, `JsonReader`, nothing held) reads `vue-current-live` into tournaments (`id`, `name`, `start_date`, `end_date`) and `vue-live-matches` into the same `Event` the SportMicro parser fills: id `match_detail.code` (prefixed `bwf-`), the sides from `t1p1_player_model.name_display` (`Hsiang Chieh CHIU`; `name_short1` is the initials form `CHIU H C`, the fallback) + `t1p2…` for a pair, `/`-joined as SportMicro writes pairs, so `SportMicroParser.surnames` and `abbreviate` are reused, games from `live_detail.team1_g1_score … team2_g3_score` (null = not played; `0` for the next game while `Waiting to start`, which counts as not begun unless the match is `P`), the state from `live_detail.match_state` (`P` = playing, the one code the app's template names; `S` = waiting between games) and `match_state_name` (`In Progress`, `Waiting to start`) / `status_name` through `StateNormaliser`, which gains the Match Centre's words (`playing` → live; `warm up`, `warming up`, `on court`, `coming up`, `waiting to start` → upcoming; `completed` → final), `winner` (1 or 2, null while live) deciding the sides' `winner`, `live_detail.event` + `round` as the detail (`MS - R32`), `court_name` as the session, `duration` ignored. A game over with no next one begun, `In Progress` or `Waiting to start`, reads as the interval, as in ADR-044. The field names and words here are from the 2026-11-12 recordings; the first version, written from the template alone, read the initials as the name, counted the waiting match's `0` third game as played (so a 1-1 match read as upcoming) and guessed `Playing` for the live word.
  - **Failure is a row, never a crash.** A challenge page that does not clear, a timeout, an HTTP error on the main frame, a JS error, a 4xx from an API call or a changed shape (`IllegalStateException` from the parser) all end as an `IOException("BWF site unavailable: <reason>")` from `scoreboard`, which the repo's existing backoff and `stale` handling take; the repo now keeps each key's last error (`ScoreRepo.lastError(key)`), and the Scores app's Home shows **"BWF site unavailable"** with the reason as a row above the events while the source is BWF and its last fetch failed (the same row shell as the key row, ADR-044), and the picker's Badminton column says so in place of tournaments. The launcher's pill simply has no badminton line.
  - **Fixtures.** `vue-current-live` was recorded through the WebView on the emulator on 2026-11-10 (`livescore/src/test/resources/fixtures/bwf/current-live-20261110.json`: Kumamoto Masters Japan 2026 and VICTOR Kaohsiung Masters 2026, both running 10–15 November). `vue-live-matches` answered `{"results":[]}` when recorded (00:10 in Kumamoto, no match on court), kept as `live-matches-empty-20261110.json`; `live-matches-handmade.json` is written by hand from the field names the Match Centre's own template reads (`tournament.*.js`), with a `_note` saying so, and stays for the edge cases it exercises (retired, walkover, pairs, a surname in capitals wherever it falls). On 2026-11-12 a live day was recorded with `tools/dev/record_bwf_fixtures.sh`: `current-live-20261112.json` (four tournaments), `live-matches-5216-20261112.json` (three Kumamoto matches in progress, singles and doubles, the real name fields) and `live-matches-5844-20261112.json` (a match `Waiting to start` at one game each with a `0` third game, two in progress), which `BwfParserTest` reads. The script re-records them through the real loader on the emulator (`BwfRecordTest`, an instrumentation test that runs only with `-e bwf_record true`).
  - **Memory**, measured on `HikViewer_TV_1GB` on 2026-11-10 (`dumpsys meminfo`, TOTAL PSS of the real companion process with its Home open, polled every second): 48 to 68 MB before the visit, 106 to 116 MB for the two or three seconds the page loads (the capture itself took 1.2 s), and 97 to 99 MB from the moment the WebView is destroyed, flat for the next 30 s. So the visit costs about 50 MB at its peak and **about 30 MB of private memory stays for the life of the process** (Native Heap 16 MB, Unknown 7 MB, the WebView provider's `.apk` and `.jar` maps 16 MB private clean, `WebViews: 0` in the object count): Chromium's browser side cannot be unloaded from a process once it has started, which `destroy` and the trim do not change. On this AVD the renderer ran inside the companion's process (no `sandboxed_process` appeared). The process is a background one the system reclaims between fetches; **a separate `:bwf` process for the loader, which would return every byte when it exits, is the follow-up if the owner wants the memory back** and is not built here.
  - **Memory, re-measured at review on 2026-11-11** (same AVD and method, Home of the companion open, then Settings → Refresh now): 73.4 MB before the visit, 115 MB at the peak, 114 MB from the moment the WebView is destroyed and flat for the next minute, `WebViews: 0` in the object count. Of the 114 MB only 26.5 MB is private dirty (Native Heap 10 MB, Dalvik 2 MB, Unknown 7 MB); the rest of what stays is the WebView provider's code mapped into the process (`.apk mmap` 32 MB, `.so mmap` 16 MB, `.jar mmap` 10 MB, mostly clean pages the kernel can drop under pressure but PSS counts while mapped). So **about 40 MB of PSS stays for the life of the process after the first visit**, more than the 30 MB first measured, and the Settings row says so; the separate process remains the follow-up that would return it.
- Rejected: reading the API bodies in `shouldInterceptRequest` (the re-fetch meets the challenge); a separate process for the loader (the right fix for the retained 30 MB, but a bound service and IPC for an experimental option; deferred); keeping the WebView alive between fetches (tens of MB held on a 1 GB TV for a 5-minute cadence); a `WebView` in the launcher (the launcher has no network and never will, ADR-005); the fansite's `vue-live-scores` (404); making BWF the default or removing SportMicro (the owner wants the keyed source to stay the default and the WebView to be opt-in); a per-source live cadence shorter than 5 min for BWF (a Chromium page load a minute on a 1 GB TV); a Robolectric test of the bridge path (Robolectric's `ShadowWebView` runs no JavaScript, so the loader is tested through its pure `PendingCapture` state machine and the source through a fake loader).
- Consequences: `BwfParserTest` (the hand-made and the two recorded days), `BwfWebViewSourceTest`, `PendingCaptureTest`, `WebViewPageLoaderTest` (the host allowlist), `SourceRegistryTest` (routing by the preference), `ScoreProviderTest` (the job's refresh leaves the WebView source out), `PrefsTest`, `BadmintonGateTest` and new `StateNormaliserTest` cases on the JVM; `SettingsTest` on the emulator for the Badminton source row; `THIRD_PARTY_NOTICES.md` gains a BWF entry (site content © Badminton World Federation, no affiliation, an experimental read of a public page that may stop); `docs/providers.md`, the README and the CHANGELOG name the option.
